VPC COMPONENTS
VPCInternet Gateway
→Enables internet access for PUBLIC subnets (bidirectional)
→Attached to VPC, not a subnet
≠ NOTPrivate subnets need NAT Gateway for outbound. IGW alone ≠ private subnet internet access.
VPCNAT Gateway
→Private subnet outbound internet only — no inbound connections
→IPv4 only — use Egress-Only IGW for IPv6
→Lives in a public subnet, routes traffic for private subnets
VPCEgress-Only Internet Gateway
→IPv6 equivalent of NAT Gateway — outbound only
→Prevents internet from initiating connections to IPv6 instances
TRIGGER"IPv6 private subnet outbound" → Egress-Only IGW (not NAT Gateway — IPv4 only)
VPCSecurity Groups vs NACLs
SGInstance-level firewall · Stateful · Allow rules only
NACLSubnet-level firewall · Stateless · Allow AND Deny rules
→SGs: return traffic automatically allowed (stateful)
→NACLs: must explicitly allow both directions (stateless)
KEY"Block a specific IP address" → NACL only. Security Groups cannot deny specific IPs — allow-only.
VPCSubnets & AZs
→Subnet exists within ONE AZ only — cannot span AZs
→Can create multiple subnets per AZ
→VPC scope = spans multiple AZs in ONE Region — regional, NOT global
→Egress-Only Internet Gateway = IPv6 outbound-only traffic from private subnet
TRAP"Subnets span multiple AZs for HA" → WRONG. You achieve HA by putting resources in multiple subnets, each in a different AZ.
HYBRIDOn-Premises → AWS Connectivity
Site-to-Site VPNEncrypted IPsec tunnel over the public internet. Fast to set up. Performance depends on internet connection.
Direct ConnectDedicated private physical line — never touches the public internet. Consistent performance, lower latency, higher cost. Takes weeks to provision.
VPN ComponentsCustomer Gateway = YOUR on-premises router (your side). Virtual Private Gateway = AWS side, attaches to VPC. Both required for Site-to-Site VPN.
→Direct Connect also terminates at the Virtual Private Gateway on the AWS side
→Private subnet route table must include: on-prem CIDR → Virtual Private Gateway so EC2 can reach on-premises resources
EXAM TRIGGER"Bypasses the public internet entirely" → AWS Direct Connect. "Encrypted tunnel over the internet" → AWS Site-to-Site VPN. "AWS side of VPN or Direct Connect" → Virtual Private Gateway. "On-premises router" → Customer Gateway.
HYBRIDVPC Peering vs Transit Gateway
PeeringDirect private connection between exactly 2 VPCs — no on-prem. Works cross-region. Non-overlapping CIDRs required.
TGWHub-and-spoke — connect many VPCs + on-prem to one central hub. Specify a threshold — if connecting many, use TGW.
→15 VPCs full mesh = 105 connections. Transit Gateway = 15 connections.
TRIGGER"Many VPCs connecting to each other" → Transit Gateway. "Two VPCs talk directly, no on-prem" → VPC Peering.

IAM MUST-KNOW FACTS
GLOBALIAM is a global service — create users once, works from anywhere in the world. No per-region setup.
FREEIAM is free — no charge per user, group, role, or policy.
CANNOT DOIAM cannot create local OS accounts on servers. That is OS-level management, not cloud IAM.
GROUPSGroups CANNOT be nested. Users CAN belong to multiple groups.
ROOTRoot user = account owner. Enable MFA immediately. Never use for daily tasks. Never create access keys for root.
USERIAM User
→Represents one specific person — individual named identity (e.g. john@company.com)
→Has long-term credentials — username/password for Console, access keys for CLI/API
→Best practice: one IAM User per person — never share accounts
→Permissions granted directly OR via group membership
TRIGGER"Individual person needs access to Console or CLI with long-term credentials" → IAM User
GROUPIAM Group
→Collection of IAM Users — share permissions for many users at once
→Attach one policy to the group → all users in the group inherit it
→Groups cannot be nested — no groups within groups
→A user can belong to multiple groups
→Groups have NO credentials of their own — permission containers only
TRIGGER"All developers should have the same S3 read access" → create a Group, attach policy, add users
ROLEIAM Role
→For services, applications, or cross-account access — NOT for individual people day-to-day
→Provides temporary credentials — automatically rotated, no long-term keys stored
→EC2 needs S3 access → attach a Role to the EC2 instance (instance profile)
→Lambda, ECS tasks, cross-account access all use Roles
TRIGGER"Service needs access to another service" → IAM Role. "Temporary permissions, no long-term credentials" → IAM Role. Never hardcode keys.
POLICYIAM Policy
→JSON document that defines permissions — what actions are allowed or denied on which resources
→Structure: Effect (Allow/Deny) · Action (s3:GetObject) · Resource (ARN)
→Managed policies — AWS pre-built or customer-created, reusable across users/roles
→Inline policies — embedded directly into one specific user, group, or role
→Explicit Deny always wins — even if another policy grants access
TRIGGER"JSON document that allows or denies actions" → IAM Policy. Policies are attached to Users, Groups, or Roles.
ROOT USERRoot User — Account Owner
→Created when you first set up the AWS account — has full unrestricted access to everything
→Enable MFA immediately — this is the first thing to do after account creation
→Do NOT use for daily tasks — create IAM Users with least-privilege instead
→Never create access keys for the root user
ROOT-ONLY TASKSChange support plan · Close the account · Change account name/email · Restore IAM admin permissions · Enable MFA delete on S3 · Register as seller in Marketplace
SSOAWS IAM Identity Center
→Formerly called AWS Single Sign-On (SSO)
→Single sign-on across multiple AWS accounts and business applications
→Users sign in once → access all assigned accounts without re-entering credentials
→Integrates with Microsoft Active Directory, Okta, and other identity providers
→Works with AWS Organizations — manage access across the entire org from one place
TRIGGER"Single sign-on across multiple AWS accounts" → AWS IAM Identity Center. "Federated access / SSO" → IAM Identity Center (not basic IAM Users).

ConsoleUsername + Password (+ MFA if enabled)
API/CLIAccess Key ID + Secret Access Key
EC2 SSHKey Pair (never confused with access keys)
KEYNever embed access keys in code → use IAM Roles instead. Access keys ≠ key pairs.
ROLESIAM Roles
→Grant temporary credentials to services/applications
→EC2 needs S3 access → assign a Role to the EC2 instance
→No long-term credentials stored → more secure than access keys
→Cross-account access, Lambda permissions, EC2 instance profiles

GROUPSIAM Groups

IAM BEST PRACTICESIAM — When to Use What
"EC2 instance needs to access S3" → IAM Role attached to EC2 (NEVER hardcode access keys)
"Application needs temporary credentials" → IAM Role (not IAM User)
"Person logging into Console or CLI" → IAM User with access keys for CLI, password for Console
→Principle of least privilege = grant only permissions required for the task, nothing more
→Root user = enable MFA immediately, never use for daily tasks, no access keys
→IAM Group = easiest way to apply permissions to many users at once
→Cross-account access = IAM Role with trust relationship (not sharing credentials)
❌Never hardcode access keys in application code — always use IAM Roles for EC2/Lambda

ACCESS TOOLSSDK vs CDK vs CLI vs Console
ConsoleAWS Management Console · Browser-based visual UI — humans exploring or managing resources manually
CLIAWS Command Line Interface = CLI · Terminal commands and shell scripts — automate tasks from the command line
SDKAWS Software Development Kit = SDK · Libraries for Python (boto3), JavaScript, Java, .NET, Go, Ruby — let your application code call AWS services programmatically. Trigger: "programmatic access from application code"
CDKAWS Cloud Development Kit = CDK · Write infrastructure definitions IN code (Python, TypeScript, Java) → compiles to CloudFormation → provisions AWS resources. Trigger: "define infrastructure using a programming language"
KEY DIFFERENCESSDK = your app talks TO AWS services (upload file, query DynamoDB). CDK = you DEFINE what AWS infrastructure to build. CLI = command line access/automation. Console = visual browser UI.
DO NOT MIX THESE UP"Programmatic access to AWS from application code" → SDK (not CLI). "Automate via shell script" → CLI. "Define infra in Python/TypeScript" → CDK. "JSON/YAML templates" → CloudFormation. Read the trigger phrase carefully — these appear as wrong answers for each other.

SUPPORT PLANSFull Names — Support Tiers Compared
→AWS Basic Support · Free. Billing questions only. No technical cases. 7 core Trusted Advisor checks.
→AWS Developer Support · Business-hours email only. 7 core checks. No Support API.
→AWS Business Support · 24/7 phone + chat. Full Trusted Advisor. Support API. No TAM.
→AWS Enterprise On-Ramp Support · Pooled TAM team. 30-min critical SLA.
→AWS Enterprise Support · Dedicated TAM. 15-min critical SLA. Support Concierge.
❌Support API starts at Business — Basic and Developer do NOT have it
❌TAM starts at Enterprise On-Ramp — Business does NOT have a TAM
